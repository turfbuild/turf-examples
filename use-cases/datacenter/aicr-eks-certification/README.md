# A certified GPU cluster, as one graph: EKS, the AICR stack, and NVCRE

> **This is a target-state spec, not a runnable example.** It passes
> `terraform validate` and 27 mocked `terraform test` runs. No engine can take
> it end to end today: each Turf engine is missing features it uses, and the
> wait action's provider, `turfbuild/kubewait`, is not on a registry yet.
> [Prerequisites](#prerequisites) lists exactly what is missing. Nothing below
> has run against a real cluster.

NVIDIA's [AI Cluster Runtime](https://github.com/NVIDIA/aicr) (AICR) validates
its recipes on real GPU clusters in a nightly UAT pipeline. On EKS, that
pipeline:

1. creates the cluster with [`mchmarny/cluster`](https://github.com/mchmarny/cluster), a Terraform actuator that takes one YAML file;
2. installs the AICR stack with helmfile or Argo CD;
3. runs a training smoke;
4. tears everything down.

The steps between those tools are GitHub Actions: waiting for GPU nodes,
polling custom-resource status, re-authenticating, sweeping out-of-state load
balancers before the VPC can go, and retrying destroys. The cluster is one
graph, the stack another, and the edges between them live in shell.

This example writes that lifecycle as **one configuration**, and adds the step
AICR's UAT does not yet run: an
[NVCRE](https://github.com/NVIDIA/cluster-readiness-engine) (NVIDIA Cluster
Readiness Engine) certification of the GPU pools.

```
modules/eks-cluster ──► modules/cluster-prereqs ──► modules/eks-compute
 VPC, IAM, KMS, EKS       ENIConfig ─► vpc-cni         system NG, GPU ASGs (EFA)
 kube-proxy, OIDC         (was local-exec kubectl)     ─► coredns, metrics-server, …
        │                                                     │
        └──────────── endpoint ───────────► terraform_data.cluster_contents
                                            [before_destroy: no LoadBalancer Services]
                                                      │
                                                      ▼
                                           bundle/  (AICR recipe → 16 module calls)
                                           … kubeflow-trainer ─► nvcre
                                                      │
                                                      ▼
                          modules/certification: namespace, nodes, identity,
                            [before_create: GPU census]
                            Certification
                            [after_create: Succeeded | Failed]
                            [after_destroy: TrainJobs = 0, Pods = 0]
                                                      │
                                                      ▼
                          modules/cuj-train: TrainJob [after_create: Complete | Failed]
```

Square brackets are **actions**: waits attached to the lifecycle event they
guard. They are the one generic primitive this example adds: specified in
[`kubewait-action.md`](kubewait-action.md), implemented by `turfbuild/kubewait`.

## Converging it (predicted)

Deferral turns "the provider's cluster doesn't exist yet" into "plan it next
round". Three rounds are predicted. aicr-stack measured two on kind; this one
needs a third because a custom-resource instance can't be planned until its CRD
is served.

1. **Round 1: all the AWS infrastructure in `eks-cluster`.**
   - The ENIConfigs defer on `provider_config_unknown`: the kubernetes provider is configured from the cluster's endpoint.
   - Everything downstream defers on `absent_prereq`, whole modules at a time.
2. **Round 2: from the ENIConfigs to the certification namespace.**
   - ENIConfigs, then vpc-cni, then the node groups and ASGs.
   - Then the Deployment add-ons, then the barrier.
   - Then all 16 bundle releases in dependency order, ending with kubeflow-trainer and nvcre.
   - Then the certification namespace.
   - The Certification and the TrainJob defer: their kinds are not served yet.
3. **Round 3: the certification and the smoke.**
   - Read the GPU nodes.
   - **Census gate:** exactly the expected nodes, all Ready, nodewright's runtime taint gone, GPUs allocatable.
   - Create the Certification.
   - **Terminal wait:** up to 60 minutes, streaming per-category progress.
   - Create the TrainJob.
   - **Completion wait:** up to 20 minutes.

The apply that finishes round 3 means something a green `terraform apply` could
not mean before: *these nodes, booted from these launch templates, running this
stack, passed these NVCRE categories*. The `certification` output names them.

## Why the waits are actions

A Certification that *finished*, nodes that are Ready *and* untainted, a
namespace with *no* TrainJobs left: these are states of objects, not their
existence.
- `helm_release.wait` knows only workloads.
- `kubernetes_manifest`'s `wait {}` has no failure predicate, so a failed Certification waits out its whole timeout.
- A `local-exec kubectl wait` runs at create time only.

An action attached to a lifecycle event is the missing shape. The same
primitive gates a create, holds the resource's dependents, holds a teardown,
and confirms one.

| Wait | On | Event | On failure | What it replaces in AICR's UAT |
| --- | --- | --- | --- | --- |
| GPU census | Certification | `before_create` | halt | `gpu_census_verdict` |
| Certification terminal | Certification | `after_create` | taint (re-run next `up`) | draft AICR PR #2519's `waitForCRETerminal` |
| TrainJob and Pod drains | Certification | `after_destroy` | halt | ADR-025's "confirm children are gone" |
| TrainJob finished | TrainJob | `after_create` | taint | `phase_train`'s poll loop |
| No LoadBalancer Services | teardown barrier | `before_destroy` | halt | the graceful LB delete before VPC destroy |

Full semantics, schema and HCL: [`kubewait-action.md`](kubewait-action.md).

## Graceful teardown (assumed)

`turf destroy` walks the graph in reverse. In-cluster objects are deleted
through the **old** cluster's endpoint, before the cluster goes, in this order:

1. The TrainJob.
2. The Certification. The `after_destroy` drains then confirm NVCRE's TrainJobs and pods are gone.
3. The namespace.
4. The 16 releases, in reverse dependency order. nvcre and kubeflow-trainer are still running while the Certification's children finalize.
5. The barrier's `before_destroy` gate: no LoadBalancer Service may remain. By now the graph has removed every Service it created. The gate catches the rest and **halts with their names**; it does not delete them.
6. The Deployment add-ons, the ASGs, the system node group, the launch templates.
7. vpc-cni, then the ENIConfigs. Upstream never deleted these.
8. Access entries, OIDC, IRSA roles, then the cluster.
9. The VPC's contents, then the VPC.
10. The KMS key (scheduled, 30-day window) and the log groups.

**Replacing the cluster is destroy-then-create.** Every IAM, security-group,
launch-template and ASG name carries `deployment.id`, so two generations cannot
coexist. The in-cluster contents are condemned through the old endpoint first,
and rounds 2 and 3 repeat against the new cluster.

## Re-certification and day 2

NVCRE makes a Certification's spec immutable, so a certificate can only be
re-earned by a new one. `terraform_data.identity` lists what a certificate is
*of*:
- the cluster endpoint and Kubernetes version;
- the GPU nodes' EC2 instance IDs;
- each certified pool's launch template ID and version, and its ASG;
- the digest of the AICR recipe;
- the spec itself.

When any of these changes, the old Certification is deleted, then a new one is
created. It is destroy-first, so two runs never contend for the same GPUs.

| Change | Re-certifies? | Why |
| --- | --- | --- |
| Raise a GPU pool's `capacity` | yes | New instances, so new instance IDs, in the round after the ASG changes. The census's expected count follows. |
| Change the system pool, or add a CPU pool | no | Not part of the identity. |
| Add a pool to `certification.pools` | yes | New pool identity and node set. |
| Kubernetes minor upgrade | yes | Version, plus a new AMI and launch template if `image_id` is unpinned. |
| New AMI or capacity reservation for a GPU pool | yes | The launch template version changes. Whether the ASG then rolls its instances is **not verified** (it points at `$Latest`). If it does not, the old nodes are re-certified. |
| Regenerate `bundle/` | yes | The recipe digest changes. |
| Change categories, thresholds or options | yes | The spec changes. Immutable, so this is a replace. |
| Runner egress IP changes | no | `public_access_cidrs` updates in place, as upstream. |

## The typed surface: YAML → variables

`mchmarny/cluster` reads one YAML file through `yamldecode()` and `try()`. Here
each section is a variable. Its `optional()` defaults are upstream's `try()`
defaults, and validation blocks replace the JSON Schemas, which were editor-only
and had drifted from what the HCL reads. `terraform.tfvars.example` is AICR's
aws-h100 lane rendered this way, with placeholder account, reservation, AMI and
role values.

| `deployment.state` | *dropped*: the backend / Turf workspace | |
| `deployment.destroy` | *dropped*: `turf destroy` is a verb, not a field | |

| — | `certification`, `cuj_train` | new: what UAT scripts |

**What the validations catch** that the YAML path did not:
- an id too long for IAM role names;
- more private than public subnets, which upstream turns into an index error because each private subnet routes through the NAT gateway of the same index;
- a zone used twice in a tier;
- inverted `min`/`desired`/`max`;
- unknown taint effects;
- enum typos in reservation preference and market type;
- an **empty capacity-reservation target**, which upstream renders as the ARN `…:group/`. AICR's GB200 lane config currently carries that value.

**What they do not catch.** Measured on Terraform 1.16.2: an object-typed
variable silently drops attributes it doesn't declare. So `instanceTyp = …` is
ignored, exactly as `try()` ignored it. Types stop wrong types and bad values,
not typos.

## Deviations from `mchmarny/cluster`

The port is faithful: resource names, addresses, locals and upstream's own
comments are kept, and upstream's tests pass unchanged (`tests/compute.tftest.hcl`,
`tests/cluster.tftest.hcl`). Every ported file says what changed. In summary:

1. **YAML → typed variables**, with identical defaults (above).
2. **ENIConfigs are resources.** They are `kubernetes_manifest`s, one per zone,
   built exactly as `templates/eni-config.ytpl` built them. Where a zone is in
   both tiers the worker entry wins, as upstream's apply order made it. They
   are now updated and destroyed; the `local-exec` never did either.
3. **vpc-cni sits with the ENIConfigs, and compute depends on both.** Upstream
   relied on nodes not booting before custom networking was applied within
   one apply. Rounds make that a real race, so it is now an edge.
4. **coredns, metrics-server, ebs-csi and cloudwatch-observability follow the
   node groups.** They are Deployments, and should not race the nodes they
   schedule onto.
5. **The account precondition is the aws provider's `allowed_account_ids`.** Same
   check, and neither Turf engine models resource preconditions.
6. **Status is outputs, not a file.** `local_file.status` wrote the full
   ClusterStatus next to the config, where a containerized run lost it. The
   same facts are now in state. The `local` and `time` providers are gone.
7. **Local backend,** as in every example here. Upstream's S3 backend had no
   state locking; use one with locking (`use_lockfile = true`) for real.
8. **Workers are a map keyed by name.** Resource addresses are unchanged.
9. **Two never-read fields are dropped** (`disableEndpoints`, `gpuType`).

**Kept as found**, and worth asking the author about:
- The ENIConfigs point at the system and worker subnets and security groups, not the `pod` subnets carved from the secondary CIDR.
- `p5e`, `p5en` and `p6-b200` are not in the GPU-family map. They get the generic EFA layout, but not the default GPU taint, unless `accelerator` is set.

## Prerequisites

What would have to exist for an engine to take this end to end:

| Needed | MCP engine | Restate engine |
| --- | --- | --- |
| `action` blocks and `action_trigger`, including destroy events | supported | refused (tier 2) |
| `on_failure = taint` | treated as `halt` | — |
| `ignore_changes` on nested paths (ASG / node-group `desired_*`) | nested paths are no-ops | refused |
| `for_each` on data sources (three in the port) | not verified | refused |
| forwarding `timeouts {}` (ASG delete 30m, GPU pools) | not forwarded | not verified |
| builtin `terraform_data` (shims, identity, barrier) | not served | supported |
| graceful teardown through the prior-state provider | built | built |
| **the same prior-state pin for destroy-event actions** | **new** | **new** |
| deferral: unknown provider config; CRD kind not served | built | built |

Beyond the engines:
- **`turfbuild/kubewait` on a registry**: the action provider in [`kubewait-action.md`](kubewait-action.md) is built and tested ([turfbuild/terraform-provider-kubewait](https://github.com/turfbuild/terraform-provider-kubewait)) but not on a registry, so it is installed locally (see [Validating](#validating-and-testing)).
- **`--deployer terraform` in AICR**: it exists only on a fork today (see [Regenerating `bundle/`](#regenerating-bundle)).
- **NVCRE in a recipe**: no stock AICR overlay includes it, so `aicr/data` adds it (below).
- **Transport assertion**: draft AICR PR #2519 also checks that NCCL actually ran over EFA; nothing here does. Category `thresholds` are the partial substitute.

## Outside the graph, deliberately

These stay out, on purpose:
- AICR's **conformance run and signed evidence** (`aicr validate --phase all`, `aicr evidence verify`): keyless signing needs the CI job's own identity.
- **TestGrid ingest.**
- **Reservation leasing and scheduling**: the nightly matrix, the daytime hold, the pre-batch guard.
- **Capacity pre-flight checks.**
- **Tenancy bootstrap**: the state bucket, CI OIDC federation.
- **Orphan sweeping.**
- **Supply chain** for the actuator image.

`deployment.tags` plus the kept `Cluster` / `ManagedBy = cluster-toolkit` tags
keep upstream's `tools/delete-eks` sweeper working against clusters made here.

## Validating and testing

```sh
terraform init -backend=false
terraform validate
terraform test
```

No credentials are needed. Every provider is mocked in the tests.

**Installing `turfbuild/kubewait`.** It is not on a registry yet, so `init`
needs a local copy. In a checkout of
[turfbuild/terraform-provider-kubewait](https://github.com/turfbuild/terraform-provider-kubewait):

```sh
make mirror                              # builds 0.1.0 into .mirror/ and writes dev.tfrc
export TF_CLI_CONFIG_FILE=$PWD/dev.tfrc  # serves turfbuild/kubewait from .mirror/
```

Then run `terraform init -backend=false` here. A rebuilt 0.1.0 has a new
checksum, and `init` rejects it even with `-upgrade`. After each rebuild, run
the `terraform providers lock` command that `make mirror` prints, here, then
`init` again.

**What `validate` checks in the waits.** The provider's schema is the one the
spec defines, so a misspelled attribute or a string where a count belongs is an
error. The provider also rejects the five configurations the spec rules out, such as
`settle` not shorter than `timeout` or CEL that does not compile, and names the
offending line. Values from variables and data sources are unknown to
`validate`; Terraform checks them again at plan time.

| Test file | What it covers |
| --- | --- |
| `compute.tftest.hcl` | Upstream's six compute tests, **assertions unchanged**: the GB200 / GB300 / explicit-accelerator / CPU EFA layouts and taints. Plus the add-on ordering. |
| `cluster.tftest.hcl` | Upstream's creator-access-entry test, unchanged. Plus ENIConfigs: one per zone, the worker tier wins. |
| `prereqs.tftest.hcl` | The ENIConfig manifests match upstream's template; no vpc-cni means no add-on. |
| `certification.tftest.hcl` | The spec (`nodeNames`, `taintSelectors`, `gangScheduler`, options). Re-applying keeps the certificate. A new launch-template version makes a new one. |
| `variables.tftest.hcl` | The aws-h100 lane plans through the whole graph with upstream's defaults. Each validation rejects its target input, including the empty reservation target. |
| `lifecycle.tftest.hcl` | The whole graph applies, re-applies without re-certifying, and tears down, all under mocks. |

The tests check wiring, not waiting: a mocked action cannot block. The waiting
is tested in the provider's repository, against a real API server (envtest) and
under Terraform 1.16.2.

Measured along the way, on Terraform 1.14.0, 1.15.0, 1.16.0 and 1.16.2:
destroy-event triggers and `on_failure` first appear in **1.16.0**; 1.14 and
1.15 reject both. Hence `required_version = ">= 1.16.0"`.

Also measured, on 1.16.2: **`terraform destroy` never lets an action block.**
In a destroy walk Terraform turns a failed destroy-event action into a warning,
whatever `on_failure` says, and deletes anyway. A failed `before_destroy` gate
halts only a destroy that is part of an ordinary apply, such as a replace. So
under the Terraform CLI, the drains and the LoadBalancer gate warn at full
teardown instead of halting it. The teardown order above assumes an engine that
honours them.

## Regenerating `bundle/`

`bundle/` is generated. `aicr/data` is the input: AICR's stock
`h100-eks-ubuntu-training-kubeflow` overlay, replaced by the same file plus one
`componentRef` for nvcre. This follows AICR's
[Enabling NVCRE](https://github.com/NVIDIA/aicr/blob/main/docs/user/component-catalog.md#enabling-nvcre)
guidance: kubeflow-trainer comes from the `platform-kubeflow` mixin the overlay
already has.

To regenerate from the committed recipe:

```sh
aicr bundle --recipe bundle/recipe.yaml --data aicr/data --output bundle \
  --deployer terraform --terraform-child-module --terraform-cluster-rollover
```

To re-resolve the recipe from its criteria first (after changing `aicr/data`,
or to pick up a newer AICR catalog), resolve to a path **outside** `bundle/`.
The bundler writes its own `bundle/recipe.yaml`, and resolving into that path
leaves the unbundled form behind:

```sh
aicr recipe --service eks --accelerator h100 --os ubuntu --intent training \
  --platform kubeflow --data aicr/data --output /tmp/recipe.yaml
aicr bundle --recipe /tmp/recipe.yaml --data aicr/data --output bundle \
  --deployer terraform --terraform-child-module --terraform-cluster-rollover
```

The result:
- 17 components as 16 module calls (kubeflow-trainer carries its post chart);
- 18 `depends_on` edges, five levels deep;
- nvcre alone at the bottom, behind kubeflow-trainer.

Both routes reproduce the committed `bundle/` byte for byte, which makes
`git diff bundle/` the check that it is current. As for
aicr-stack, `--deployer terraform` is not in NVIDIA's AICR yet: this bundle was
generated from the fork's submission,
[turfbuild/aicr#3](https://github.com/turfbuild/aicr/pull/3), at its head
`54fc5a2e`.
