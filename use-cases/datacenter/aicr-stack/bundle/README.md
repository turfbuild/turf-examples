# AICR bundle — Terraform

Generated by AICR dev for `criteria(service=kind, accelerator=h100, intent=inference, os=, platform=)`.

16 Helm releases, as 14 module calls in `main.tf` —
one per component. A component's pre-manifest, post-manifest and readiness-gate
releases live inside its module, so `depends_on` on the call covers all of them.

## Deploy

This bundle is a **child module**. It has no provider configuration of its own
and no backend: the configuration that calls it owns both.

```hcl
provider "helm" {
  kubernetes = {
    host                   = kind_cluster.dc.endpoint
    cluster_ca_certificate = kind_cluster.dc.cluster_ca_certificate
    client_certificate     = kind_cluster.dc.client_certificate
    client_key             = kind_cluster.dc.client_key
  }
}

module "stack" {
  source = "./bundle"
}
```

Then `terraform init && terraform apply` in the calling configuration.

Regenerate without `--terraform-child-module` to get a standalone root module
that reads a kubeconfig instead.

## When the cluster is in the same configuration

Wiring the provider to a cluster resource, as above, means its attributes are
unknown until the cluster exists. That is fine: `helm_release` does not contact
the API server during planning, so an unknown provider configuration does not
block the plan. One `terraform apply` creates the cluster and installs the
whole bundle behind it.

This is why the bundle is a child module rather than a root module with its own
provider block. A module carrying a provider block cannot take `depends_on`,
`count` or `for_each`, which is exactly what a caller needs to sequence the
bundle behind the cluster that hosts it.

## The dependency graph

`depends_on` on each module call carries the recipe's `dependencyRefs`
**exactly**. A component waits for its declared dependencies and for nothing
else, so independent components apply concurrently.

That is a stronger guarantee than the tier-based deployers can give.
`argocd` projects the graph onto integer sync-waves and `helmfile` onto nested
level files; both are total orders, so a component ends up waiting for every
sibling at the prior depth rather than for its own dependencies. Only `flux`
(`dependsOn`) and this deployer keep the graph.

The edge sits on the module **call**, not on the `helm_release` inside it. A
`depends_on` on a call is a fact about everything the module contains, so the
ordering survives the module growing a second resource.

Components that expand into more than one release — a `-pre` manifest chart, a
`-post` chart, a readiness gate — chain internally, and a dependent waits for
the **last** release in that chain, not just the primary chart.

## What `wait` does and does not buy you

`var.wait` (default `true`) makes each `helm_release` wait for its workloads
to become ready, which is what turns an ordering edge into a readiness edge.

It does **not** wait on custom-resource status. A component whose real signal
is a CR condition — `ClusterPolicy.status.state=ready`,
`NicClusterPolicy.status.state=ready` — will report applied while that
condition is still pending. Regenerate with `--readiness-hooks` to get an
explicit gate: each gated component grows a `-readiness` release whose Job
blocks the dependents until the signal actually passes, and which re-runs
whenever that release is upgraded.

## Layout

```
main.tf                     # the module calls, and the graph
versions.tf                 # required_providers
variables.tf                # wait/timeout/atomic
outputs.tf
modules/component/          # the shared module every call resolves to; holds the
                            #   component's pre / chart / post / readiness releases
NNN-<component>/            # values.yaml, cluster-values.yaml, and either
                            #   upstream.env (upstream chart) or
                            #   Chart.yaml + templates/ (bundled chart)
```

The `NNN-<component>/` folders are the standard AICR bundle layout, written by
the same code that writes them for `--deployer helm` and `--deployer helmfile`.
`install.sh` in each folder is part of that layout and is unused here.

## Editing

`main.tf`, `versions.tf`, `variables.tf`, `outputs.tf` and `modules/component/`
are generated — regenerating overwrites them. Per-cluster settings belong in
the calling configuration and in each component's `cluster-values.yaml`,
neither of which is overwritten.
